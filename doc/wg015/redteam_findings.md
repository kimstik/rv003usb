## Линза: ?

**Вердикт:** The plan's factual base and phase ordering are strong, but its centerpiece — the G1 gate — is designed in a way that systematically favors a false PASS for flash-first: the P1.4/P1.5 benches model neither I-cache eviction by the arbitrary user main loop and the C protocol layer (H1 tested on an unrealistically warm cache), nor the real RX engine's data-dependent multi-path fetch pattern (H2 is already refuted at the documented-prefetcher level — every per-bit backward branch leaves the 32-byte window — so flash-first silently rests on the undocumented I-cache alone), nor D-code flash reads that the TX loop performs on flash-resident descriptors (H3's 'all data in RAM' is un-enacted and collides with the anti-scope). The acceptance algebra is also wrong: slot errors integrate into phase with no in-packet resync, so 'per-slot ≤±2' either admits fatal accumulation or is vacuous next to the −4..+6 total-drift bound, which itself is a repurposed V003 start-phase artifact — and the proposed period histogram cannot even produce the cumulative quantity being gated. Finally, both fallbacks are mis-costed ('не трогает код' is contradicted by the repo's own lui/jr RAM-variant precedent across the 1 GB flash↔TCM gap), and LAT=1 is adopted without an integrity gate against unanimous vendor/community LAT=3 practice. Executed as written, G1 would likely pass and P3/P4 would fail with hard-to-attribute timing losses — the exact class of expensive rework the calibration phase exists to prevent. Fix the gate's benches, criterion, and fallback costing before P1; the rest of the plan is sound.

### ?-1 [BLOCKER]
**Претензия:** G1 gate (P1.4a 'холодный/горячий прогон (H1: повтор == повтор?)' and P1.5 slot emulation) measures an unrealistically warm I-cache: no bench models eviction of ISR lines by code that shares the same undocumented 2KB I-cache — the arbitrary user main loop, the C protocol layer, libc. H1's promise 'повторные пакеты детерминированы' is tested only in a quiet loop; in the real system the first traversal of each RX sub-path (bit-stuff path, EOB path, one-bit path) inside a given packet hits a cold/evicted line MID-packet, after the preamble retiming has already locked the grid — the SYNC absorber (PLAN §3 'вход ISR съедается SYNC-паттерном') cannot save mid-packet cold misses. So the gate is structurally biased toward PASS, and failure surfaces at P3 as unexplained CRC losses — the exact expensive rework G1 exists to prevent.

**Доказательство:** PLAN Р6: «H1: горячий ISR (~1.2К) целиком садится в I-cache 2К → повторные пакеты детерминированы»; PLAN P1.4(а): «холодный/горячий прогон (H1: повтор == повтор?)» — no eviction adversary anywhere in P1. Hot set is larger than the ISR: C handlers run inside the same ISR invocation (rv003usb.S:492 `c.beqz a5, usb_pid_handle_in` → rv003usb.c:162-238 in flash .text, descriptor scan c:415-433), plus user main loop between packets and keepalive every 1 ms (S:673). I-cache organization/line size/eviction: undocumented — research_flash.md GAPS 3: «Core 2 KB I-cache: organization, line size, enable/bypass/flush controls … absent from РП». First-touch of handle_bit_stuff occurs only at the first stuffed bit of a packet (rv003usb.S:396-424), i.e. mid-grid.

**Фикс:** Redesign P1.4a/P1.5: between emulated packets run an eviction adversary (execute >2-4 KB of unrelated flash code, e.g. jr through a jump table); start emulated packets with one sub-path deliberately cold (first touched mid-packet). G1 pass requires timing identical with vs without the adversary. State in Р6 that H1's 'ISR' must include the C handlers on the turnaround path.

### ?-2 [BLOCKER]
**Претензия:** H2 ('straight-line код в пределах префетч-буферов = 0ws, miss только на дальних бранчах') is factually wrong for the actual RX engine, and the P1.5 synthetic slot ('load-DATA + работа + store-TGL') is far more linear than the real code, so it cannot falsify H2. The RX bit loop is NOT straight-line: each bit takes a data-dependent path among bit_process → handle_zero_bit / handle_one_bit / handle_bit_stuff / is_end_of_byte, spanning roughly S:298–S:424 (~300 bytes) with a backward branch every bit — every one of those targets is 'дальний' relative to the documented 2×128-bit (32-byte) prefetch window, so at the documented-hardware level EVERY slot misses, and the miss pattern varies with packet content (data-dependent jitter). Flash-first therefore rests entirely on the undocumented I-cache, which the plan never states. A tight synthetic loop fits in the two buffers (or trivially in cache) and will show zero jitter no matter what the real code would do → G1 false-pass.

**Доказательство:** rv003usb.S:304-424: `c.beqz a0, handle_one_bit` (S:323), `c.beqz s0, handle_bit_stuff` (S:382), `HANDLE_NEXT_BYTE(is_end_of_byte,…)` (S:313-317, 351, 384, 400), `c.bnez s1, bit_process` (S:362, 393, 424) — multi-target, content-selected paths. research_flash.md §3: prefetcher = 2×128-bit buffers, «miss both → goto 1», «РП gives no cycle formula for miss cost»; research_core_irq.md §6: «every branch out of the 32-byte buffered window eats a nondeterministic flash-line refill». PLAN P1.5: «синтетический 32-тактный цикл (load-DATA + работа + store-TGL)» — single body, one branch.

**Фикс:** Make the P1.5 emulation structurally isomorphic to the real slot: ≥3 alternative slot bodies placed at realistic distances (100–300 B apart), selected per-iteration by PRBS data, backward branch each slot — or port the RX skeleton (zones z1/z2 only) early and drive it with a pattern generator before declaring G1. Rewrite H2 honestly: 'flash-first is possible only if the undocumented I-cache makes the multi-path loop deterministic'.

### ?-3 [BLOCKER]
**Претензия:** G1 criterion algebra is wrong. (a) Slot durations integrate: the sampling grid IS the instruction stream and master has no in-packet resync (the plan anti-scopes the branchless resync), so per-slot error accumulates as phase — 'per-slot джиттер ≤±2' admits a random walk (±2·√90 ≈ ±19 cycles 1σ-scale excursions) or a systematic bias of up to 62 500 ppm, 6.8× outside master's own measured eye tolerance (9217 ppm). (b) Enforcing the second criterion (90-bit drift within −4..+6) implies mean per-slot error ≤6/90 ≈ 0.07 cycles — making the ±2 criterion vacuous or misleading. (c) The proposed measurement, «гистограмма периодов», mathematically cannot distinguish correlated from independent jitter and cannot reconstruct worst-case cumulative excursion, i.e. the bench does not even produce the quantity the second criterion gates on. (d) Most fundamentally: the codebase's only timing tool is STATIC padding, which can correct a deterministic per-path constant but can never correct genuine nondeterminism — so measured true jitter of ±2 should mean FAIL-to-flash, yet the gate passes it.

**Доказательство:** PLAN G1: «per-slot джиттер ≤±2 тактов и суммарный дрейф на 90-битном пакете в окне −4..+6 → флеш»; P1.5: «гистограмма периодов — прямой ответ». No in-packet resync in master: rv003usb.S:327-331 «Can we resync time here? … I was thinking we could put the resync code here» (unimplemented TODO); PLAN §6 anti-scope excludes the branchless resync branch. Padding-only method: rv003usb.S:20 `nx6p3delay`, S:22-25 `VOOXDELAY`; stack_portability.md §2 «Loops are hand-unrolled instruction slots padded to 32 cycles». Eye tolerance scale: branch_notes.md — master eye 9217 ppm (ones); «worst-case all-ones payload dies at ~+5000 ppm» without resync; runfromram warning: «changing fetch timing silently breaks the cycle ledgers».

**Фикс:** Replace the criterion: (1) each RX/TX path must be repeat-DETERMINISTIC (zero variance) across repeats and cache-state preparations — any true nondeterminism ⇒ flash FAILS, since only static padding exists; (2) per-path means trimmed to exactly 32 by z7; (3) residual drift gated by max cumulative excursion over sliding 90-slot windows across ≥10^4 PRBS packets (log cumulative sums, not just a period histogram).

### ?-4 [MAJOR]
**Претензия:** The −4..+6 number is a start-of-grid PHASE-skew tolerance measured once, at done_preamble, on CH32V003 with that build's specific sample placement — the plan repurposes it as the accumulated-drift budget over a 90-bit packet in G1. ### ?-5 [MAJOR]
**Претензия:** H3 ('все данные ISR в RAM' — 'принимается сразу как правило (дёшево)') is neither cheap nor sufficient: USB descriptors are const .rodata in flash, and the TX inner loop reads descriptor bytes from flash INSIDE the cycle-counted bit loop — a D-code flash read every 8 TX bits, with РП-documented D-code-over-I-code priority stalling instruction fetch mid-slot. Enforcing H3 literally means copying all descriptors to RAM with pointer fixup — a C-layer change the plan's own Р3 ('rv003usb.c трогаем минимально') and anti-scope ('изменения C-протокольного слоя сверх швов Р3') forbid, and for which no plan step exists. Leaving them in flash means P1/G1 never measured the dominant TX perturbation class (D-code + in-flight I-prefetch collision), so GET_DESCRIPTOR transfers can jitter even after G1 passes → discovered at P4.

**Доказательство:** rv003usb.c:424: `e->opaque = (uint8_t*)dl->addr;` (descriptor_list = const, flash); rv003usb.c:236 `usb_send_data( sendnow, tosend, 0, sendtok )`; rv003usb.S:887-890 `load_next_byte: XW_C_LBU(s0, a0, 0)` — byte load inside the counted TX loop. research_flash.md §3: «Чтение D-code шины имеет приоритет» (РП 7.1, manual.txt:2014-2015) — «jitter source if constants live in flash». PLAN Р6 H3 wording + PLAN §6 anti-scope + Р3.

**Фикс:** Decide now, in Р6/Р8: either (a) add an explicit init-time copy of descriptor payloads to RAM (small, bounded; makes H3 actually true — acknowledge the C-seam cost), or (b) add a flash-resident lbu into the P1.5 TX-slot emulation and a G1 sub-criterion for D-code/I-fetch collision determinism. Silence guarantees rework at P4.

**Вердикт:** The plan's measurement-first skeleton is sound and most of its raw arithmetic checks out against the source (32 cyc/bit, SYNC 8×32=256, 48000/ms keepalive with modular-sub wrap already handled, 300 ns ≈ 14 cycles, −4..+6 correctly quoted from S:186-188, claim-deferred-to-tail PLIC usage is legal per the gateway semantics and adds nothing to the ≤7.5-bit turnaround). ### ?-1 [BLOCKER]
**Претензия:** Р2-z3 claims TX is 'запись BSHR → запись DATAOUTTGL (NRZI = toggle по нулевому биту: одна store)'. Toggle-only cannot express 3 of the 6 BSHR write sites: the initial K preset before output enable, the SE0/EOP (both lines driven LOW — an absolute state unreachable by a fixed toggle mask because the NRZI end state is data-dependent), and the J-park before release. Executed as written, no packet ever gets a valid EOP and enumeration fails.

**Доказательство:** /home/user/rv003usb/rv003usb/rv003usb.S: S:767-768 preset 'li s1, (1<<USB_PIN_DP) | (1<<(USB_PIN_DM+16)); c.sw s1, BSHR' (absolute K before CFGLR switch at S:771); S:992-993 SE0 'li s1, (1<<(USB_PIN_DM+16)) | (1<<(USB_PIN_DP+16)); c.sw s1, BSHR' (both-clear = absolute); S:997-998 J-park 'li s1, (1<<(USB_PIN_DM)) | (1<<(USB_PIN_DP+16))' (absolute). Only S:837 (preamble loop), S:948 (send_zero_bit) and S:1024 (insert_stuffed_bit) are toggle-expressible. Additionally the data-loop one-bit path (S:914-927) contains NO store at all — z3's 'одна store, значение = 0 или D±-маска' describes the preamble loop (unconditional store, S:837) but not the data loop, so the substitution changes instruction counts inside cycle-counted slots (xor s1,t1 disappears from S:947; a store may be added to the one-path), not just a register address.

**Фикс:** Respecify z3 per-site: bit-loop stores → DATAOUTTGL (constant D±-mask on the zero path, or 0/mask if made unconditional); SE0 → single DATAOUTCLR=D±mask; SE0→J → single DATAOUTSET=DM-mask; preset K → DATAOUTSET/DATAOUTCLR pair (or TGL only with a guaranteed J parked in DATAOUT, incl. first-ever TX init). Explicitly note that TX slot padding (z7) must re-balance the changed instruction sequence, not just swap the store target.

### ?-2 [MAJOR]
**Претензия:** Gate G1 (§4 P1) acceptance math is wrong: 'per-slot джиттер ≤±2 тактов И суммарный дрейф ... в окне −4..+6' treats jitter and drift as separate budgets, but S:186-188 defines −4..+6 as the TOTAL sampling-phase displacement tolerance. Drift at +6 plus jitter +2 puts a sample at +8, outside the measured window — the gate can green-light a failing flash configuration. Also, in a software-timed loop per-slot deviations are cumulative (a +1 stall shifts every later sample), so the criterion must bound the running sum at every bit, not endpoint drift plus an independent per-slot band.

**Доказательство:** /home/user/rv003usb/rv003usb/rv003usb.S:186-188: '8 extra cycles here cause errors. -5 cycles is too much. -4 to +6 cycles is OK' — a single static-offset window at done_preamble affecting all subsequent samples. PLAN.md §4 G1: 'per-slot джиттер ≤±2 тактов и суммарный дрейф на 90-битном пакете в окне −4..+6 → флеш'. No fact-base source assigns jitter a budget outside the −4..+6 total.

**Фикс:** Rewrite G1 criterion as: max cumulative sample-point displacement over the whole packet (running sum of per-slot period errors from bench-5 histogram, evaluated at every bit, worst path) must lie inside −4..+6 with margin reserved for host clock tolerance; drop the separate ±2 per-slot figure or derive it so that drift+jitter ⊂ [−4..+6].

### ?-3 [MAJOR]
**Претензия:** Р2-z4 'предустановка DATAOUT': a full-word DATAOUT write to preset the K state clobbers bit 2 of port C — the DPU pin (Р5: D+=C0, D−=C1, DPU=C2 on the SAME port). DPU drops low → the 1.5k pull-up on D− becomes a pull-down → host sees a disconnect on the first IN response. The claimed 1-store preset is not achievable with a plain DATAOUT write; the safe preset is a SET/CLR pair (2 stores) or TGL with a guaranteed prior J state.

**Доказательство:** PLAN.md Р5 puts DPU on C2, same port as D±; research_gpio.md §1: 'DATAOUT: read returns state; write drives pins (manual.txt:16874-16884)' — full 16-bit write, no masking. rv003usb never touches whole-port output state: the V003 preset uses BSHR set/clear semantics touching only D± (/home/user/rv003usb/rv003usb/rv003usb.S:767-768), and preset strictly precedes direction switch (S:768 before S:771). The plan states neither the register form nor the preset-before-OUTENSET ordering.

**Фикс:** Specify z4 as: DATAOUTSET=DP-mask + DATAOUTCLR=DM-mask (or DATAOUTTGL from parked J), never full DATAOUT; keep preset-before-OUTENSET ordering; alternatively use MASKLB masked write (documented for writes, research_gpio.md §1). Update the 'короче, чем у V003' instruction count to ~3 stores total (still shorter).

### ?-5 [MAJOR]
**Претензия:** §3 and P1.3 declare the constant part of IRQ entry latency irrelevant ('важен разброс, не абсолют'; 'константная часть неважна').
