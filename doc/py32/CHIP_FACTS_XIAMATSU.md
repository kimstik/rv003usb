# PY32 — измеренные факты (Xiamatsu), меняющие проект порта

Источники (даны пользователем, скачаны 2026-09-04, копии в scratchpad):
* https://github.com/Xiamatsu/py32f002b — README.md, 276 строк (PY32F002B/L020)
* https://github.com/Xiamatsu/py32f002a_003_030 — README.md, 493 строки (F002A/F003/F030)

Это независимые ИЗМЕРЕНИЯ на живых чипах, а не даташит. Там, где они расходятся с
RM/DS, приоритет у измерения — но помечено, чем именно проверено.

## 1. Стоимость инструкций — измерено (F002A/003/030, Flash Latency=0, ≤24 МГц)

| Операция | Тактов | Источник |
|---|---|---|
| Большинство инструкций | 1 | xm_030.md:471 |
| Ветвление взятое / невзятое | 2 / 1 | xm_030.md:472 |
| **LDR/STR к портам GPIO** | **1** | xm_030.md:473, :41 |
| LDR из Flash через PC (литеральный пул) | 2 | xm_030.md:474 |
| **LDR/STR к ОЗУ** | **4** | xm_030.md:475, :40 |

**Это ломает базовое допущение всех известных реализаций.** Grainuum, LemcUSB и
ветка py32 держат состояние в ОЗУ и свободно грузят/сохраняют внутри битовой
ячейки. На PY32 каждое обращение к ОЗУ стоит 4 такта против 1 у GPIO — в ячейке
из 32 тактов это разорительно. Автор README прямо помечает это «МИНУС !!!».

Следствия для движка:
* внутри битовой ячейки — только регистры и однотактный порт ввода-вывода;
* запись байта в приёмный буфер бюджетируется как 4 такта, а не 1;
* константы выгоднее держать в литеральном пуле флеша (2 такта), чем в ОЗУ (4);
* это, вероятно, и есть настоящая причина, почему TX-петли ветки «дотягивают до
  32 тактов только за счёт задержек флеша» — модель стоимости была неверной.

ОТКРЫТО: измерения сделаны на F002A/003/030. Действует ли «медленная ОЗУ» на
F002B (другой кристалл, общий с L020) — не проверено. Обязательный пункт стенда.

## 2. Клок: 48 МГц достижимы, но по-разному на разных деталях

### F002B — заводская константа 48 МГц СЛОМАНА
* «для F002B не объявлена поддержка HSI 48 MHz» (xm_002b.md:6) — общий кристалл с
  L020, у которого 48 МГц объявлены.
* Factory Config `[0x1FFF0104] = 0x0000B3A2` → HSI_FS=0b101 (48M), HSI_TRIM=0x13A2,
  расчётно 49.60 МГц (xm_002b.md:269-270).
* **Измерено на живом чипе: 43.12 МГц** (MCO/2 = 21.56 МГц) — xm_002b.md:172-175,
  подтверждено в сводке констант: «43.12 MHz для 48 MHz — калибровочная константа
  установлена неверно» (:209-210).
* Ошибка −10.2 % от 48 МГц. Энумерация при такой расстройке невозможна в принципе
  (LS USB требует ±1.5 %), значит **загрузить заводскую константу и работать нельзя**.

Диапазон подстройки HSI_FS=101 (xm_002b.md:249-257): min 21.7 МГц (TRIM_L=0x000,
TRIM_H=0), max1 33.4 МГц (TRIM_L=0x1FF, TRIM_H=0). TRIM_H задаёт прибавку в
процентах к этому диапазону (:232-246): +33 % при 0b0110, +41 % при 0b0111,
+50 % при 0b1000. То есть 48 МГц лежит между TRIM_H=0b0111 и 0b1000 —
**достижимо с запасом**, но только собственной калибровкой.

Опорой для калибровки может служить LSI: заводская константа даёт измеренные
32.71 кГц против номинала 32.768 кГц, то есть −0.18 % (xm_002b.md:204-206) —
этого достаточно, чтобы выйти к 48 МГц до старта энумерации. Второй опорой
служит сам кипэлайв хоста (ровно 1 мс), но он доступен только после подключения.

HSE на F002B — только вход (1–32 МГц), PLL отсутствует, поэтому внешним
генератором 48 МГц не получить.

### F002A / F003 / F030 — чистый путь через PLL
* HSI: заводские константы на 4, 8, 16, 22.12, 24 МГц; для 24 МГц измерено
  23.99 МГц, то есть −0.04 % (xm_030.md:15, xm_002b.md:207 для сравнения).
* PLL ×2, вход 16–24 МГц (xm_030.md:15), «PLL_IN — только 24 MHz» (:79).
* 24 МГц × 2 = **47.98 МГц, ошибка −0.04 %** — внутри допуска USB **без всякого
  серво**. «Проверено — PLL запускается на 48 МГц на чипах PY32F002A и PY32F003»
  (xm_030.md:336).

**Вывод: первичной целью порта следует делать F030/F003 (точные 48 МГц из HSI24×PLL2),
а F002B — второй целью с обязательной самокалибровкой.** Это разворачивает выбор
детали, сделанный в PLAN.md (там первичным был F002B).

## 3. Прочее, влияющее на порт

* Flash Latency = 0 держится до 30 МГц (F002B, xm_002b.md:259) и до 24 МГц (F030,
  xm_030.md:466) → на 48 МГц латентность ненулевая, XIP-тайминги плавают.
* MCO на PA7 выдаёт не выше ~35 МГц (xm_002b.md:261) — прямой замер 48 МГц через
  MCO невозможен, только с делением.
* ISP-бутлоадер по UART при BOOT0=1 (xm_030.md:374) — путь восстановления без SWD.
* NRST требует «SWD-Delay» ~100 мс в стартап-файлах (xm_030.md, раздел errata).
* OTP 128 байт на F002B — место для per-board константы калибровки.
* Инструменты: PY32CubeProgrammer, edbg (модифицированный, с lock/unlock), pyOCD;
  в mainline OpenOCD поддержки нет.

## 4. Что это меняет в PLAN.md

1. Первичная деталь: F030/F003 вместо F002B (§2).
2. Модель стоимости движка: ОЗУ 4 такта / GPIO 1 такт — пересчитать весь леджер,
   вынести всё горячее в регистры (§1).
3. Для F002B добавить задачу самокалибровки HSI по LSI до энумерации, и только
   потом серво по кипэлайву (§2).
4. Проверить на стенде, действует ли «медленная ОЗУ» на F002B.
